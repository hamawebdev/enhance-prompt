# Findings

## F-IN-01 — Do not run the pipeline as equal-status peers that coordinate through shared state; Cursor tried exactly that first and it failed.
- Evidence: "Our initial approach gave agents equal status and let them self-coordinate through a shared file." — IN-01
- Evidence: "With no hierarchy, agents became risk-averse." — IN-01
- Evidence: "Twenty agents would slow down to the effective throughput of two or three, with most time spent waiting." — IN-01
- Bears on: run mechanics | question B
- Strength: described practice (experiment report, no controlled numbers beyond the throughput remark)

## F-IN-02 — The design that worked at Cursor has isolated workers that never talk to each other and return one written handoff to whoever requested the task; the handoff carries concerns and deviations, not only results.
- Evidence: "They're unaware of the larger system. They don't communicate with any other planners or workers." — IN-02
- Evidence: "they write up a single handoff that the system submits to the planner that requested the task" — IN-02
- Evidence: "The handoff contains not just what was done, but important notes, concerns, deviations, findings, thoughts, and feedback." — IN-02
- Bears on: handoff | run mechanics | question B
- Strength: described practice

## F-IN-03 — Give each agent one role; an agent asked to plan, do, review and judge at once degraded, and the owner of the whole scope should not do the work itself.
- Evidence: "We found it was being given too many roles and objectives simultaneously" — IN-02
- Evidence: "It does no coding itself." — IN-02
- Evidence: "Too little structure and agents conflict, duplicate work, and drift. Too much structure creates fragility." — IN-01
- Bears on: run mechanics
- Strength: described practice

## F-IN-04 — Cognition, the loudest critic of multi-agent systems, now says the workable shape is a manager that splits, isolated children that execute, and the manager that synthesizes; free networks of negotiating agents are "a distraction".
- Evidence: "We think the unstructured-swarm approach, arbitrary networks of agents negotiating with each other, is mostly a distraction." — IN-04
- Evidence: "The practical shape is map-reduce-and-manage: a manager splits work, children execute, the manager synthesizes and reports back." — IN-04
- Bears on: question B | run mechanics
- Strength: opinion backed by described production practice

## F-IN-05 — Agent-to-agent messaging and shared state are the weak points of current models: messaging does not happen unless engineered, and agents wrongly assume the other agent knows what they know.
- Evidence: "Cross-agent communication, a sub-agent writing messages back to its manager to be passed to other agents in the agent team, doesn't happen by default, because models haven't been trained in environments where it needed to." — IN-04
- Evidence: "Agents assume they share state with their children when they don't." — IN-04
- Bears on: question B | handoff
- Strength: described practice

## F-IN-06 — Keep one writer of the artifact and let the other agents contribute judgment (framing, review); multi-agent set-ups work when writes are single-threaded.
- Evidence: "multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions" — IN-04
- Bears on: run mechanics | requirements
- Strength: described practice

## F-IN-07 — A reviewer that shares no context with the author finds more; Cognition reports this as its best-performing configuration and gives numbers.
- Evidence: "we found this technique to work best when the coding and review agents do not share any context beforehand." — IN-04
- Evidence: "Devin Review catches an average of 2 bugs per PR, of which roughly 58% are severe" — IN-04
- Bears on: checker | question B
- Strength: measured result (vendor-internal, method not published)

## F-IN-08 — A blind checker's findings must come back to an agent that holds the full instructions, which decides what to act on; otherwise the loop runs long, adds out-of-scope work or overrides the user.
- Evidence: "This is key to preventing looping, disobeying the user, doing work that is out of scope, and so on." — IN-04
- Evidence: "Often the system will loop through multiple code-review cycles, finding new bugs each time (which isn't always great since it can take a while)." — IN-04
- Bears on: checker | run mechanics | question B
- Strength: described practice

## F-IN-09 — On strictly sequential work, adding inter-agent coordination lowers quality; where several agents are used, a central orchestrator contains errors far better than independent agents.
- Evidence: "every multi-agent variant we tested degraded performance by 39-70%" — IN-10
- Evidence: "independent multi-agent systems (agents working in parallel without talking) amplified errors by 17.2x" — IN-10
- Evidence: "Centralized systems (with an orchestrator) contained this amplification to just 4.4x." — IN-10
- Bears on: question B | run mechanics
- Strength: measured result (180 configurations, four benchmarks; none of the benchmarks is requirements writing)

## F-IN-10 — Google's own long-horizon harness partitions context on purpose and has critics verify from a clean context without the producer's reasoning.
- Evidence: "each specialized agent receives only the exact files and tools it needs for a specific step" — IN-11
- Evidence: "critics and auditors challenge and verify results from clean contexts without the original producer's reasoning" — IN-11
- Bears on: checker | question B | handoff
- Strength: described practice (first-party research post)

## F-IN-11 — Google ships both models and assigns them differently: an orchestrated pipeline over isolated subagent contexts for a sequential solve-and-verify loop, and a shared message board only for broad work whose pieces are independent.
- Evidence: "a sequential solve-and-verify loop refined from prior trajectories" — IN-11
- Evidence: "The pipeline coordinator dispatches specialized workers in isolated subagent contexts" — IN-41
- Evidence: "`/swarm` works best when the pieces of a task can proceed independently." — IN-40
- Evidence: "Every worker is its own agent, so a swarm uses quota much faster than a single conversation." — IN-40
- Bears on: question B | run mechanics
- Strength: described practice (IN-40 and IN-41 are undated docs; IN-11 is dated)

## F-IN-12 — In Google's sequential pipeline the original task is passed on verbatim, later workers re-read the original requirements independently, and the orchestrator checks the result against every requirement before finishing or sending it round again.
- Evidence: "hands your verbatim task and relevant conversation context to a pipeline coordinator" — IN-41
- Evidence: "Follow-up improvement workers review the original requirements independently, attempt to break or find gaps in the prior worker's output, fix any flaws, and re-run tests." — IN-41
- Evidence: "The orchestrator spot-checks the code changes and test record against every requirement in your prompt." — IN-41
- Bears on: checker | handoff | run mechanics
- Strength: described practice (undated doc)

## F-IN-13 — Choose the context mode per role: a verifier gets an isolated context so it is not anchored; a worker that continues upstream reasoning should receive that reasoning rather than rediscover it.
- Evidence: "The verifier should evaluate the work itself rather than being anchored by the supervisor's diagnosis or expectations." — IN-14
- Evidence: "Starting the worker in isolation would force it to rediscover its evidence." — IN-14
- Evidence: "Subagents spawn with a fresh context window, receiving only the task description specified by the supervisor." — IN-14
- Bears on: checker | handoff | question B
- Strength: direct recommendation

## F-IN-14 — Start from the simplest arrangement that works; if stages are fixed and sequential, fix their order in the workflow instead of letting agents decide who goes next.
- Evidence: "Use the lowest level of complexity that reliably meets your requirements." — IN-18
- Evidence: "The choice of which agent gets invoked next is deterministically defined as part of the workflow and isn't a choice given to agents in the process." — IN-18
- Evidence: "Many agentic tasks are best handled by a single agent with well-designed tools." — IN-13
- Bears on: run mechanics | question B
- Strength: direct recommendation

## F-IN-15 — Centralized subagents buy context isolation at the price of one extra model call per round trip; that is the known cost of the orchestrator model.
- Evidence: "The main agent maintains conversation context while subagents remain stateless, providing strong context isolation." — IN-13
- Evidence: "Adds one extra model call per interaction because results must flow back through the main agent." — IN-13
- Bears on: question B | run mechanics
- Strength: direct recommendation with a small worked comparison

## F-IN-16 — A maker–checker loop needs three things written down: explicit acceptance criteria for the checker, a cap on rounds, and what happens when the cap is hit.
- Evidence: "This pattern requires clear acceptance criteria for the checker agent so that it can make consistent pass or fail decisions." — IN-18
- Evidence: "Set an iteration cap to prevent infinite refinement loops, and define fallback behavior for when the cap is reached." — IN-18
- Bears on: checker | run mechanics
- Strength: direct recommendation

## F-IN-17 — Pass the next agent only what it needs: a fresh instruction set plus the necessary artifacts, not the accumulated transcript.
- Evidence: "If your agent can work without accumulated context and only requires a new instruction set, take that approach instead of providing context that doesn't help accomplish the agent's task." — IN-18
- Evidence: "The callee sees only the specific instructions and necessary artifacts—no history." — IN-12
- Evidence: "Every model call and sub-agent sees the minimum context required." — IN-12
- Bears on: handoff | question B
- Strength: direct recommendation

## F-IN-18 — Make what passes between agents explicit and structured; agents do not act on implied intent, and unstructured exchanges are where multi-agent workflows break.
- Evidence: "Typed schemas are table stakes in multi-agent workflows. Without them, nothing else works." — IN-06
- Evidence: "LLMs don't follow implied intent, only explicit instructions." — IN-06
- Evidence: "Most multi-agent workflow failures come down to missing structure, not model capability." — IN-06
- Bears on: handoff | run mechanics
- Strength: direct recommendation

## F-IN-19 — OpenAI's subagent model is the isolated-worker model: the main agent keeps requirements and decisions, subagents return summaries, the brief says what to return, and the arrangement costs more tokens.
- Evidence: "Keep the main agent focused on requirements, decisions, and final outputs." — IN-35
- Evidence: "Return summaries from subagents instead of raw intermediate output." — IN-35
- Evidence: "A good subagent prompt should explain how to divide the work, whether Codex should wait for all agents before continuing, and what summary or output to return." — IN-35
- Evidence: "subagent workflows consume more tokens than comparable single-agent runs" — IN-35
- Bears on: question B | handoff | run mechanics
- Strength: direct recommendation (undated doc)

## F-IN-20 — Cloudflare's production reviewer is a coordinator over isolated specialist sessions that return structured findings; the coordinator dedupes and judges. Their main prompt lesson: tell a checker what not to flag.
- Evidence: "Each sub-reviewer runs in its own OpenCode session with its own agent prompt." — IN-24
- Evidence: "they simply return their findings as structured XML when they finish" — IN-24
- Evidence: "It turns out that telling an LLM what not to do is where the actual prompt engineering value resides." — IN-24
- Bears on: checker | handoff | question B
- Strength: described practice (run on tens of thousands of merge requests)

## F-IN-21 — Checking must be done by something other than the agent that did the work, and the worker must hand over evidence, not a claim of completion.
- Evidence: "Critically, validation should not depend only on the team member that performed the work." — IN-23
- Evidence: "Agent Teams need separation between doing, checking, accepting, and merging." — IN-23
- Evidence: "Fluent writing or a confident summary is not enough to establish that a task succeeded." — IN-36
- Bears on: checker
- Strength: direct recommendation (IN-36 undated)

## F-IN-22 — A judge that compares the output with the original prompt earns its place: Spotify's vetoes about a quarter of agent sessions, and the usual reason is work outside the instructions.
- Evidence: "It uses the diff of the proposed change and the original prompt, and sends them to an LLM for evaluation." — IN-09
- Evidence: "the judge vetoes about a quarter of them. When that happens, the agent is able to course correct half the time." — IN-09
- Evidence: "the most common trigger is the agent going outside the instructions outlined in the prompt." — IN-09
- Bears on: checker
- Strength: measured result (internal metrics over "thousands of agent sessions"; Spotify says it has not yet built evals for the judge)

## F-IN-23 — Block and Stripe run multi-stage agent work as a fixed flow: Block starts each stage in a fresh session that reads the previous stage's written document; Stripe defines the flow in code, runs it unattended and limits the retry rounds.
- Evidence: "then starts a new session with fresh context where the agent reads that research and documents a detailed plan for execution" — IN-20
- Evidence: "Blueprints are workflows defined in code that direct a minion run." — IN-17
- Evidence: "we think there are diminishing marginal returns if an LLM is running against indefinitely many rounds of a full CI loop" — IN-17
- Evidence: "A typical minion run starts in a Slack message and ends in a pull request which passes CI and is ready for human review, with no interaction in between." — IN-16
- Bears on: run mechanics | handoff | question B
- Strength: described practice

## F-IN-24 — State the outcome, the success criteria and the constraints, and leave the path to the agent; OpenAI says this in every current guide.
- Evidence: "Describe the expected outcome, success criteria, allowed side effects, evidence rules, and output shape. Avoid step-by-step process guidance unless the exact path matters." — IN-30
- Evidence: "Start with the result, not a detailed list of steps." — IN-44
- Evidence: "Describe the result you want, not only the activity ChatGPT should perform." — IN-33

## F-IN-29 — Information the agent must always have belongs in always-loaded context, and insistent wording is fragile: Vercel measured both.

- Bears on: final-prompt shape | run mechanics
- Strength: measured result (one framework's eval suite)

## F-IN-30 — Write boundaries rather than to-do lists: constraints steer better than instructions, itemised tasks narrow the agent's attention to the items, and concrete numbers convey scope.

# Where companies disagree with each other or with the usual advice

1. **Role or persona lines.** Cognition calls "you're a senior software engineer" a gimmick (IN-04). GitHub's analysis of agent definition files says the opposite for that file type: a specific persona is one of four things the successful files share, and the starter template opens "You are an expert [technical writer/test engineer/security analyst] for this project" (IN-07). OpenAI keeps a "Role:" slot but defines it as function, context and job (IN-30); its newest Codex guide has no role at all (IN-32). Google says role definitions go first (IN-38) and its example subagent opens with an expert persona (IN-42), while the same Gemini page says to avoid "overly persuasive language". Nobody in this slice measured the effect of a role line in the window.

2. **Should the reviewer see the spec?** Cognition's clean-context reviewer deliberately works "without the spec" and reasons backward from the implementation (IN-04). Spotify's judge and Google's /boost do the reverse: they compare the output against the original prompt or "every requirement in your prompt" (IN-09, IN-41). For a requirements checker the second model is the relevant one; what all three share is that the checker does not see the producer's reasoning.

3. **Is an independent judge always worth keeping?** Spotify (IN-09), Cognition (IN-04), Salesforce (IN-23), Google (IN-11) and Microsoft (IN-18) all keep one. Cursor removed it in one iteration: "We found agents were reasonably good at following instructions to completion, so the judge was removed to keep the system simple." (IN-02), and also removed an integrator gate because it was a bottleneck (IN-01, IN-02). Cursor's case is throughput at hundreds of workers, and the same post then reports the judge-less executor claiming "premature completion"; it does not weaken the case for a checker in a three-step pipeline.

4. **Maker–checker in a shared thread or in isolation.** Microsoft files the maker–checker loop under group chat, where "all agents and humans in the loop emit output into a single accumulating thread" and praises the auditability (IN-18). Cognition, Google and LangChain want the checker's context clean (IN-04, IN-11, IN-14). Microsoft's own cap, "consider limiting group chat orchestration to three or fewer agents" (IN-18), shows the shared-thread form is treated as hard to control.

5. **Ask or assume.** The model-instruction guidance says assume, label and proceed (IN-28, IN-29, IN-30, IN-31). The same vendors' interactive products put an interview in front of long work: "Ask ChatGPT to interview you, identify constraints, and turn the result into a goal with measurable success criteria." (IN-33); Cursor's Plan Mode will "Ask clarifying questions about your requirements" (IN-03); Google's /teamwork starts with a scoping interview (IN-39); and OpenAI's Codex guide adds that outside evals "more clarification may be desirable" (IN-29). A skill that never asks is at the autonomous end of what vendors describe; the evidence supports it only together with stated, labelled assumptions (F-IN-36).

6. **Files in the task prompt.** GitHub's Copilot documentation lists "Directions about which files need to be changed." as part of an ideal task (IN-43), and OpenAI's Codex guide lists "Which files, folders, docs, examples, or errors matter for this task?" under Context (IN-34). Against that, Cognition reports that prescriptive delegation "backfires when the manager lacks deep codebase context" (IN-04), Cursor warns that listing specifics narrows attention (IN-02), and Google's /teamwork rule is "specify what, not how" (IN-39). The split follows who writes the prompt: a developer who knows the code may point at files; a prompt written without codebase knowledge for a lead that owns the project should not.

7. **How much specification.** Thoughtworks records the split directly: "Two broad camps are emerging: teams that rely on the continually improving capabilities of coding agents with minimal structure, and those that favor defined workflows and detailed specifications." (IN-25). Microsoft and Kiro sit in the second camp (IN-19, IN-21); OpenAI's and Cursor's prompt advice leans to the first (IN-30, IN-02). Thoughtworks also reports spec tools producing "overly verbose markdown outputs that increased cognitive load" (IN-25).

8. **Specific versus over-specified.** Cursor's best-practices post says "The agent's success rate improves significantly with specific instructions." (IN-03), while Cursor's research post and OpenAI warn against step lists (IN-02, IN-30). They are compatible once "specific" is read as specific about outcome, scope and checks, not about procedure.

# Question A — what this slice's evidence says

Should the prompt handed to a coding-agent lead open with an expert role ("You are a senior X")?

- Against the expert-persona opener: F-IN-39 (Cognition calls it a gimmick), F-IN-40 (OpenAI's newest Codex guidance has no role and asks for colleague-style description plus review criteria; OpenAI says personality must not stand in for goals; Google says to avoid persuasive language), F-IN-25 (trim legacy scaffolding).
- For some role statement: F-IN-39 (OpenAI's suggested structure starts with a one-to-two sentence "Role" defined as function, context and job; Google says role definitions belong at the very beginning; GitHub's file survey favours a specific persona with an operating manual), F-IN-41 (Google's subagent example).
- What the "for" evidence actually supports is narrower than "You are a senior X". OpenAI's own production opener is identity and situation ("You are Codex … running as a coding agent in the Codex CLI"), GitHub's point is that a vague persona fails and that the operating manual matters most, and both GitHub and Google are talking about standing agent-definition or system-instruction files, not a one-off task prompt delivered to an already configured lead.
- No source in this slice measured a role line's effect during the window. The only measurement near the topic is Vercel's finding that wording changes swing behaviour (F-IN-29), which argues for restraint, not for a persona.

Reading: do not open with an expertise claim. If anything precedes the goal, make it one or two plain sentences saying what position the recipient holds in this job (it owns the project, decides on the client's behalf, runs the team), then go straight to goal, audience, scope, requirements and done-criteria (F-IN-24, F-IN-26, F-IN-27). Confidence: moderate. The direction is consistent across OpenAI, Cognition and Cursor, but it rests on recommendation and opinion, the two most on-point OpenAI pages are undated, and GitHub and Google give partial support to role lines.

# Question B — what this slice's evidence says

Isolated one-shot sub-agents returning to an orchestrator, or peers sharing a task list and messaging each other, for framer → requirements writer → blind checker with a send-back loop?

- Peer coordination through shared state failed where it was tried at scale (F-IN-01), and the same team's working design has workers that do not communicate and hand back to the requester (F-IN-02).
- The best-known sceptic now endorses manager-and-children and dismisses negotiating networks; it also reports that agent-to-agent messaging does not happen by default (F-IN-04, F-IN-05).
- Measured: every multi-agent variant lost 39–70% on sequential tasks, and a central orchestrator held error amplification to 4.4x against 17.2x for independent agents (F-IN-09). This says two things for a short sequential pipeline: keep coordination overhead to the minimum, and keep a hub that sees every result.
- The checker's independence is the point of the design, and independence means a clean context: Cognition (F-IN-07), Google (F-IN-10, F-IN-12) and LangChain (F-IN-13) all say so; a peer on a shared board or task list sees the producers' discussion.
- Vendors that ship both models assign the sequential solve-and-verify loop to the orchestrated, isolated-context pipeline and the message board to broad, independent, parallel work (F-IN-11). OpenAI's Codex documentation describes the isolated model and gives its purpose as keeping the main agent on requirements and decisions (F-IN-19); I found no peer-messaging mode in the OpenAI pages read.
- A fixed sequence should be fixed in the workflow, not negotiated (F-IN-14); the loop needs criteria, a cap and a fallback (F-IN-16); the send-back should pass through an agent that holds the full instructions so it can filter findings (F-IN-08).
- Costs and caveats of the isolated model: one extra model call per round trip (F-IN-15); context is lost unless the brief carries it, so the original paste must be passed verbatim and each brief must say what to return (F-IN-12, F-IN-17, F-IN-18, F-IN-19); and a stage that continues upstream reasoning should be given that reasoning in full (F-IN-13). For this pipeline that means the requirements writer receives the framer's whole output, while the checker receives only the original paste and the draft.
- Evidence the other way is thin: Microsoft classes maker–checker under a shared thread and values the audit trail (disagreement 4), and Google's /swarm shows a verifier working on a shared board for parallel work (IN-40). Neither is offered for a short sequential chain.

Reading: use isolated one-shot sub-agents with the orchestrator as the hub that holds the paste, passes artifacts, applies the cap and reports assumptions. Confidence: high for this pipeline shape. The caveat is transfer: none of the sources studied a requirements-writing pipeline; the measured results are on coding, planning and research tasks, and the Google and OpenAI product pages that map most directly onto the question are undated documentation.
