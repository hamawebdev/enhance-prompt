# Question A

The three cases the brief asks to keep apart are labelled in each finding: **[SYS]** a role in a system prompt for a deployed product; **[TASK]** a role line at the top of a task message to an agent that already has a system prompt (this is the skill's case); **[WORKER]** specialised roles an orchestrator gives its workers.

## Evidence for opening the final prompt with an expert role

**F-OQ-A1 [TASK] Google's current Gemini 3 guidance explicitly allows a role definition at the start of the user prompt.**
> "Place essential behavioral constraints, role definitions (persona), and output format requirements in the System Instruction or at the very beginning of the user prompt." (OQ-32)

Strength: moderate. It is the only current vendor sentence found that endorses the [TASK] placement. It is for another model family and comes with no measurement.

**F-OQ-A2 [SYS, partly TASK] Anthropic's current reference still says a one-sentence role changes behaviour, and one of its own user-turn examples opens with a role.**
> "Setting a role in the system prompt focuses Claude's behavior and tone for your use case. Even a single sentence makes a difference:" (OQ-11)

> "You are an AI physician's assistant. Your task is to help doctors diagnose possible patient illnesses." (OQ-11, first line of the "Example quote extraction" user prompt)

Strength: moderate for roles in general, weak for [TASK]: the stated guidance is about the system prompt; the user-turn example shows only that Anthropic does not treat a task-level role line as harmful.

**F-OQ-A3 [TASK or SYS, placement not stated] On Claude Fable 5.2, one sentence about the model's standing toward the work changes behaviour a great deal.** This is the strongest evidence that an opening identity sentence is not inert on the newest model. Note that the sentence is about ownership and authority, not expertise.
> "You are the owner and long-term maintainer of this codebase, and its design is up to you." (OQ-12)

> "In Anthropic's testing on small coding tasks, the model consolidated duplicated code in under 10 percent of runs without the sentence and in about 75 percent of runs with it." (OQ-12)

Strength: strong that a stance sentence has effects; it says nothing about expert personas, and the same section reports costs (see F-OQ-A15).

**F-OQ-A4 [SYS] Production coding agents' system prompts open with an identity line, and OpenAI's eval-tuned Codex prompt keeps a seniority framing.**
> "You are Codex, based on GPT-5. You are running as a coding agent in the Codex CLI on a user's computer." (OQ-29; the same line opens the starter prompt in OQ-25)

> "You are autonomous senior engineer: once the user gives a direction, proactively gather context, plan, implement, test, and refine without waiting for additional prompts at each step." (OQ-25)

> "This prompt began as the default GPT-5.1-Codex-Max prompt and was further optimized against internal evals for answer correctness, completeness, quality, correct tool usage and parallelism, and bias for action." (OQ-25)

> "'You are Gemini CLI, an interactive CLI agent specializing in software engineering tasks.'" (OQ-30)

Strength: moderate that vendors keep a role in the system prompt after tuning; these are [SYS], and the "senior engineer" sentence is a behavioural instruction about autonomy rather than a claim of domain expertise.

**F-OQ-A5 [any] A role changes what the model prioritises and how deep it goes, which is what an "expert" opening is meant to buy.**
> "role prompting systematically increases expertise depth while reducing clarity." (OQ-39, abstract)

> "Role prompting performs best on advisory questions and in domains such as medicine and psychology, where structured expert framing and risk communication are intrinsically valuable." (OQ-39, abstract)

> "Personas may shift what the AI prioritizes (emphasizing regulatory concerns for compliance officers vs. market opportunities for business developers) and how it expresses outcomes (confident expert vs. cautious advisor)." (OQ-35, discussion)

Strength: weak to moderate. OQ-39 measures open-ended Q&A, not agentic coding; the OQ-35 sentence is the authors' caveat, not a measurement.

**F-OQ-A6 [TASK] A rebuttal argues the best-known null result was an artefact of putting the persona in the user prompt under a system prompt.**
> "Five core mechanisms precluded detection before data collection began: baseline contamination elevating the starting point to near-ceiling, system prompt hierarchy subordinating experimental manipulation, impossible expert specifications collapsing to generic competence, format constraints suppressing reasoning processes, and provider exclusion limiting generalizability." (OQ-37, abstract)

Strength: weak (abstract only; its own positive result is on a hand-picked subset of hardest items). It also cuts the other way for the skill: if a system prompt "subordinates" a user-turn persona, then a role line pasted as the lead's first user message is exactly the placement expected to have little effect.

## Evidence against

**F-OQ-A7 [TASK] Anthropic's guidance for prompts typed into Claude Code names what makes them work, and a role is not among the patterns.** The stated criterion is new information; a role line gives the lead none.
> "A specific prompt helps for the same reason, because it gives Claude information it doesn't already have." (OQ-06)

> "**Describe the outcome, not the steps.** Say what you want and let Claude find the files." (OQ-09)

> "**Give it a way to check its own work.** Ask for run, test, compare, or verify in the same prompt so Claude iterates instead of stopping after one attempt." (OQ-09)

> "**State the measurable target.** When the goal is performance or coverage, give the metric and threshold so completion is unambiguous." (OQ-09)

Strength: strong for the surface (first message of a Claude Code session), with the caveat that the case against the role line is by omission: neither page mentions role lines at all, for or against. Their "What you can stop doing" table (OQ-06) does not list role lines either.

**F-OQ-A8 [TASK] OpenAI's guidance for the first message to its coding agent has the same shape: four parts, no role.**
> "A good default is to include four things in your prompt:" (OQ-26)

> "**Constraints:** What standards, architecture, safety requirements, or conventions should Codex follow?" (OQ-26)

> "**Done when:** What should be true before the task is complete, such as tests passing, behavior changing, or a bug no longer reproducing?" (OQ-26)

Strength: strong as cross-vendor convergence on Goal / Context / Constraints / Done-when for a coding agent's task message.

**F-OQ-A9 [TASK and SYS] OpenAI's newest-model guidance contains no persona advice and warns that scaffolding written for older models now hurts.** The "Prompting best practices" section of OQ-23 covers writing style, task completion, coding style and frontend design; none of its recommended prompt snippets assigns an expert role.
> "With more capable models, what used to require a lot of handholding and scaffolding no longer does." (OQ-24)

> "Models have gotten much better at understanding nuance and ambiguity, so overly specific guidance can now hinder results where it previously helped." (OQ-24)

Strength: moderate (direction of travel; the persona point is again by omission).

**F-OQ-A10 [TASK] The best-controlled accuracy study tested exactly the skill's placement (persona text at the top of the user prompt, under an unchanged system prompt) and found no reliable gain.**
> "For each trial, the user prompt consisted of the persona text (when present) followed by the question and answer options in a fixed template." (OQ-35, "How We Prompted the AI")

> "When persona prompts do matter, they are more likely to reduce accuracy than to increase it." (OQ-35, discussion)

> "role instructions that are too narrow can cause models to under-utilize their actual knowledge." (OQ-35, discussion)

Strength: strong for factual accuracy on multiple-choice benchmarks. Limits: six OpenAI and Google models (GPT-4o, GPT-4o-mini, o3-mini, o4-mini, Gemini 2.0 Flash, Gemini 2.5 Flash), no Claude model, no agentic or coding task.

**F-OQ-A11 [SYS and TASK] A 2026 mechanism study finds expert personas damage knowledge-dependent work, including coding, and that longer personas damage more.**
> "For tasks that depend on pretrained knowledge retrieval accuracy (e.g., MMLU), persona prompts should be avoided entirely—they consistently damage performance." (OQ-36)

> "On MMLU, all expert persona variants damage accuracy, with the minimum persona suffering the least (overall: 68.0% vs. 71.6% baseline)." (OQ-36, Figure 1 caption)

The paper also reports the MT-Bench coding category as "consistently degraded by expert persona prompts" (OQ-36, §3.1b).

Strength: moderate. Limits: six open-weight models (among them Qwen2.5-7B, Mistral-7B, Llama-3.1-8B and two DeepSeek-R1 distillations), none a current frontier model; MT-Bench scores are LLM-judged; in its reasoning-distilled models any long persona prefix raised the reasoning, coding and STEM scores regardless of which persona it was, so the direction of the coding effect is model-dependent.

**F-OQ-A12 [SYS] The one pre-registered 2026 study on frontier models and code generation, including Claude Opus, found engineer personas change output length, not correctness.**
> "On Claude Opus, the minimalist engineer persona reduced visible output by 30% (33% in provider tokens) without improving correctness, while the thorough engineer persona increased output without a correctness gain." (OQ-38, abstract)

> "These results are consistent with personas acting as Model-Dependent behavioral-policy biases rather than universal quality interventions." (OQ-38, abstract)

Strength: moderate and the most on-point measurement found (Claude, coding, engineer personas). Limits: abstract only, 480 completions, 12 tasks, single-shot generation, not an agent session.

**F-OQ-A13 [TASK] In a prompt that already carries many constraints, adding an expert persona is one more constraint that can interact badly.**
> "individually neutral or beneficial constraints can combine to cause substantial degradation" (OQ-40, abstract)

> "the largest interaction is -12.2 pp on GPT-4o-mini for JSON + expert persona + moderate urgency." (OQ-40, abstract)

Strength: weak to moderate (older OpenAI models; the newer GPT-4.1 family was "largely resistant"; abstract only). Relevant because the skill's final prompt is dense with requirements.

**F-OQ-A14 [any] Across 38 expert roles, role prompting moved style, not capability.**
> "Overall, our findings suggest that persona prompting primarily reshapes response characteristics rather than broadly improving capability, and that multi-metric evaluation is necessary for understanding its effects." (OQ-39, abstract)

Strength: moderate.

**F-OQ-A15 [TASK or SYS] On Fable 5.2 an identity sentence is not free: it buys behaviour the user may not want.**
> "With this prompt, output tokens rose by about 70 to 80 percent and the model made changes nobody had asked for, many of them new tests and documentation." (OQ-12)

> "In Anthropic's testing, some instructions and interventions designed for earlier models raised cost, caused side effects, or no longer had an effect." (OQ-12)

Strength: moderate. It shows the cost side of F-OQ-A3 and the general risk of carrying older prompt habits forward.

**F-OQ-A16 [SYS] In Claude Code the model's role lives at system-prompt level; Anthropic describes additions as leaving it untouched.**
> "It doesn't modify Claude's role; it just adds instructions to its default role." (OQ-21, on appending to the system prompt)

Strength: moderate. A pasted first message sits below that system prompt and the project instruction files; a second, narrower identity in the user turn competes with a role the lead already has.

Background, outside the window (not counted in the verdict's strength): Anthropic's own prompt-engineering article of 2025-11-10 says the same thing directly, see "Background" below (OQ-B1); Zheng et al. found no benefit across 162 roles (OQ-B4).

## Evidence about where a role does pay off (system prompts, worker specialisation, tone)

**F-OQ-A17 [SYS] All three vendors put identity in the system or developer prompt of a deployed agent.**
> "Baseline identity and role: Define the agent's persona and primary function—for example, "You are a database administrator agent."" (OQ-31)

> "Identity: Describe the purpose, communication style, and high-level goals of the assistant." (OQ-28, first section of a developer message)

Plus F-OQ-A2 (Anthropic) and F-OQ-A4 (Codex CLI, Gemini CLI). Strength: strong that [SYS] is the conventional home.

**F-OQ-A18 [WORKER] Anthropic recommends specialised prompts for workers when behavioural modes conflict, and its worker examples open with role lines; its orchestrator example gets a job description instead.**
> "When a single agent must switch between conflicting behavioral modes, separating into specialized agents with tailored system prompts produces more consistent results." (OQ-14)

> "You are a senior code reviewer ensuring high standards of code quality and security." (OQ-02, example subagent system prompt)

> "You coordinate platform integrations. Route requests to the appropriate specialist:" (OQ-14, the orchestrator's system prompt in the same article whose workers are "You are a CRM specialist.")

> "I asked another agent to critique the design of the project from the perspective of a Rust developer, and make structural changes to the project to improve the overall code quality, and another to work on documentation." (OQ-18)

> "The only structure we gave the team was a hierarchy, consisting of one lead and 999 helpers. We told the lead to split the problem into parts and assign them to the helpers." (OQ-22)

Strength: strong that role specialisation belongs to workers and that leads are given a function and authority, not an expertise persona. No source measured an expertise line for the orchestrator specifically; that gap is real.

**F-OQ-A19 [WORKER] Anthropic's newest reviewer example drops the expert persona for a statement of the reviewer's situation; OpenAI's does likewise.**
> "You're reviewing code you didn't write. Compare the changed files against the spec you're given," (OQ-06, `.claude/agents/reviewer.md`)

> "Review code like an owner." (OQ-27, example `reviewer` agent instructions)

Strength: moderate. Even where a role line is conventional, current examples state the stance and the criteria rather than seniority.

**F-OQ-A20 [SYS] Personas reliably help tone, format-following and safety alignment.**
> "Conversely, for alignment-dependent tasks such as format-following generation, safety, and preference satisfaction, an expert persona consistently helps." (OQ-36)

> "Personas certainly play a role in shaping the tone and presentation of output (OpenAI 2025a)." (OQ-35, discussion)

Strength: moderate. None of these is what the skill's final prompt needs from the lead.

**F-OQ-A21 [TASK] What does pay off in a task message is stating ownership and authority when that latitude is wanted** (F-OQ-A3), with the documented caveat:
> "Leave the ownership sentence out where the user owns the code and wants it changed as little as possible." (OQ-12)

## Verdict, with confidence and the specific rule the skill should follow

**Do not open the final prompt with an expert role. Confidence: medium-high (about 75%).**

Why the evidence favours "against": every current vendor statement that recommends a role places it in the system prompt of a deployed agent (F-OQ-A2, A4, A17) or in a worker's prompt (A18); the two vendor pages that describe a good first message to a coding agent list goal, context, constraints and done-criteria and no role (A7, A8); the measurements on user-turn or code-generation personas show no correctness gain and some harm (A10, A11, A12); and the lead already has a system-prompt role that the pasted message cannot replace (A16). The "for" side has one cross-vendor sentence permitting the placement (A1) and good evidence that roles shift emphasis and tone (A5, A20), which the final prompt can get more precisely by naming the standards. The confidence is not higher because no source ran the direct test (same task brief to a Claude Code lead, with and without an opening expert line), and because the case against in Anthropic's and OpenAI's coding-agent pages is by omission.

The rule:

1. **The final prompt never starts with "You are a/an [expert]…" and contains no expertise persona anywhere.** It opens with the goal and who it is for.
2. **The role the framing expert identifies is used inside the run only**, as the specialisation line of the requirements expert's brief ([WORKER], supported by F-OQ-A18).
3. **In the final prompt the role is translated into things the lead can act on:** the domain context the expert would assume, the named standards and conventions the expert would apply (written as constraints), the audience, what is out of scope, and done-criteria with a way to check them (F-OQ-A7, A8).
4. **Standing and authority are stated as facts, in one or two plain sentences, only as far as the latitude is wanted:** that the lead decides on the client's behalf, owns the result and runs the team. This is the one identity-like statement with a measured effect (F-OQ-A3); it also raises output volume and unrequested changes (F-OQ-A15), so the skill should include it deliberately and pair it with the out-of-scope list, not add it by default wording such as "you are the owner of this codebase" when the request is a narrow change (F-OQ-A21).
5. **If a perspective matters for part of the work, attach it to that work, not to the lead:** "have the checkout flow reviewed from the perspective of X" or "staff a worker who specialises in X" (F-OQ-A18).

## What would change the verdict

- A direct A/B on the skill's own outputs (for example ten representative pastes, final prompt with and without an opening expert line, run in fresh lead sessions and graded blind against the done-criteria) showing a reliable gain for the role line. No published source ran this.
- The lead being started with a replaced system prompt (a custom `--agent`, an output style, an SDK session with a custom system prompt). Then there is no default role and the expert role belongs in that system prompt, per F-OQ-A2 and A17.
- The final prompt being aimed at a Gemini-based agent, where the vendor explicitly allows the role at the start of the user prompt (F-OQ-A1).
- The deliverable being judged mainly on voice or register (client-facing copy, advisory writing), where personas do help (F-OQ-A5, A20).
- A full-text reading of OQ-37 or a replication showing user-turn expert personas raising correctness on current Claude models in agentic work.

# Question B

Terms: a **subagent** here means a non-fork subagent spawned with the Agent tool; a **fork** inherits the whole conversation and is a different thing (it matters below); **teammate** means an agent-team member.

## Evidence for subagents

**F-OQ-B1 The agent-teams page itself sends sequential, dependent work to subagents or a single session.**
> "For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective." (OQ-01)

> "Use subagents when you need quick, focused workers that report back. Use agent teams when teammates need to share findings, challenge each other, and coordinate on their own." (OQ-01)

Strength: strong (the product's own selection criterion, and the run is sequential, short and dependent).

**F-OQ-B2 A chain of subagents routed by the caller is a documented pattern.**
> "For multi-step workflows, ask Claude to use subagents in sequence. Each subagent completes its task and returns results to Claude, which then passes relevant context to the next subagent." (OQ-02)

Strength: strong.

**F-OQ-B3 A skill running in the session can start subagents; nothing comparable is documented for teams.**
> "**Skill + Subagent** | A skill spawns subagents for parallel work | `/audit` skill kicks off security, performance, and style subagents that work in isolated context" (OQ-05)

Strength: strong for subagents. For teams the docs only say Claude forms one when asked or when it names an agent while the feature is enabled (see the mechanics table).

**F-OQ-B4 Independent checking by a fresh-context subagent is Anthropic's stated practice, and separation is measured to help.**
> "in the terminal, `/code-review` reviews the diff in a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code." (OQ-06)

> "A fresh reviewer does help, because it hasn't seen your reasoning, which is a different thing from delegating." (OQ-06)

> "having a separate grader check Claude's work against a rubric improved task success by up to 10 points over a standard prompting loop, with the largest gains on the hardest problems." (OQ-19)

> "Then a subagent reviews the diff with fresh context." (OQ-20)

> "But tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work," (OQ-17)

Strength: strong for a separate, fresh-context checker; the 10-point figure is Anthropic-internal testing on structured file generation.

**F-OQ-B5 Verification is the decomposition that survives the "telephone game", because it needs the artifact and the criteria, not the history.**
> "Verification subagents succeed because they sidestep the telephone game problem." (OQ-14)

> "The verifier does not need to understand why the artifact was built as it was. It only needs to determine whether the artifact meets the specified criteria." (OQ-14)

Strength: strong, and it matches the checker's brief exactly (original paste as criteria, final prompt as artifact).

**F-OQ-B6 Anthropic's pattern guidance: generator-verifier and orchestrator-subagent first; teams are for long-running independent work.**
> "For most use cases, we recommend starting with orchestrator-subagent. It handles the widest range of problems with the least coordination overhead." (OQ-15)

> "Choose orchestrator-subagent when subtasks are short, focused, and produce clear outputs." (OQ-15)

> "Parallel workload, independent long-running subtasks" (OQ-15, the situation its summary table maps to "Agent Teams")

Strength: strong.

**F-OQ-B7 Other vendors' measurements point the same way for sequential work and for hierarchy over peers.**
> "on tasks requiring strict sequential reasoning (like planning in PlanCraft), every multi-agent variant we tested degraded performance by 39-70%." (OQ-33)

> "Centralized systems (with an orchestrator) contained this amplification to just 4.4x." (OQ-33; independent agents amplified errors "by 17.2x")

> "architectures without centralized verification tend to propagate errors more than those with centralized coordination." (OQ-34, abstract)

> "With no hierarchy, agents became risk-averse." (OQ-42, on peers self-coordinating through a shared file)

> "They don't coordinate with other workers or worry about the big picture." (OQ-42, on the worker role that replaced it)

Strength: moderate (different harnesses and tasks; OQ-33's sequential penalty applies to any multi-agent split, see F-OQ-B14).

**F-OQ-B8 Subagents structurally cannot ask the user; teammates are built to be talked to.** The run must never ask the user anything.
> "The first filter removes these tools, even when listed in the `tools` field:" (OQ-02; the list that follows includes `AskUserQuestion`)

> "You can also talk to any teammate directly without going through the lead." (OQ-01)

> "Teammate permission prompts appear in the lead session, so approve them there yourself." (OQ-01)

Strength: strong (mechanical).

## Evidence for teammates

**F-OQ-B9 Teammates keep their context across rounds, which a send-back loop uses.**
> "Teammates stay alive across many assignments, accumulating context and domain specialization that improve their performance over time." (OQ-15)

> "When subagents need to retain state across invocations, agent teams are the better fit." (OQ-15)

Strength: moderate in April 2026, weak now for Claude Code: the current docs let a subagent be resumed with its full history (mechanics table, send-back row), which removes most of this advantage for a three-round loop.

**F-OQ-B10 Routing everything through the coordinator loses detail; peers that message each other skip a relay hop.**
> "The orchestrator becomes an information bottleneck." (OQ-15)

> "After several such handoffs, critical details are often lost or summarized away." (OQ-15)

> "Each call still hands back a lossy summary" (OQ-16, on subagents called as tools)

Strength: moderate. This is the real weakness of the subagent design for a checker-to-writer loop. The published mitigation is verbatim artifacts, not peer messaging (F-OQ-B16).

**F-OQ-B11 The docs name review and mutual challenge as a team strength.**
> "**Research and review**: multiple teammates can investigate different aspects of a problem simultaneously, then share and challenge each other's findings" (OQ-01)

> "Sequential investigation suffers from anchoring: once one theory is explored, subsequent investigation is biased toward it." (OQ-01)

Strength: weak for this use. The examples are parallel investigations; the run here is one writer and one checker, and a checker that debates the writer is no longer blind.

**F-OQ-B12 One large vendor frames the maker-checker loop as a shared-thread conversation, and Anthropic's long-running harness let generator and evaluator iterate directly.**
> "The maker-checker loop is a specific type of group chat orchestration in which one agent, the maker, creates or proposes something, and another agent, the checker, evaluates the result against defined criteria." (OQ-44)

> "The two iterated until they agreed." (OQ-17, generator and evaluator negotiating a sprint contract)

Strength: weak to moderate. In OQ-17 the exchange ran through files, not messages (F-OQ-B16), and the runs were hours long; OQ-44's shared thread is chosen for transparency and human oversight, not for an independent check.

**F-OQ-B13 In a session with agent teams enabled, the skill may get teammates whether it wants them or not.**
> "a subagent that Claude names launches as a teammate, so teams can form even when you didn't ask for one." (OQ-01)

Strength: strong as a fact the skill must handle; it is not a reason to prefer teammates.

## Evidence that cuts against both: whether the framer and the writer should be separate agents at all

The brief did not ask this, but the evidence on sequential, dependent work says it plainly enough that leaving it out would misreport the sources.

**F-OQ-B14 Splitting sequential phases of the same work across agents is the decomposition Anthropic warns against; verification is the exception.**
> "Dividing by type of work (one agent writes features, another writes tests, a third reviews code) creates constant coordination overhead. Each handoff loses context." (OQ-14)

> "Sequential phases of the same work. Planning, implementation, and testing of the same feature share too much context." (OQ-14, listed under "Problematic decomposition boundaries")

> "Blackbox verification. A verifier that only needs to run tests and report results does not require implementation context." (OQ-14, listed under "Effective decomposition boundaries")

> "In our comparisons across several enterprise deployments, a single agent with skills frequently outperformed both the one-prompt-for-everything design and the subagent design on quality, and often at a lower cost and latency per task." (OQ-16)

> "They are effective at verification, parallel work, and modular permissioning." (OQ-16, on subagents)

> "Handing the same task to a subagent doesn't make the answer any better." (OQ-06)

Strength: strong. Framing then requirements is a planning phase feeding a writing phase of the same artifact; the published evidence supports isolating the checker and gives no support for isolating the framer from the writer. If the skill keeps them as two subagents, the handoff has to be verbatim (F-OQ-B16).

**F-OQ-B15 Even the separate checker is model-dependent: on some current models a mandated verifier is overhead.**
> "If your prompt contains explicit verification instructions ("include a final verification step for any non-trivial task," "use a subagent to verify"), remove them: instructions like these cause over-verification on Claude Opus 5," (OQ-13)

> "The practical implication is that the evaluator is not a fixed yes-or-no decision. It is worth the cost when the task sits beyond what the current model does reliably solo." (OQ-17)

Strength: moderate. OQ-13 is about a model re-verifying its own code; the skill's checker compares a rewrite against a source the writer may have drifted from, which is the blind, criteria-based check OQ-14 and OQ-19 still endorse in 2026. It does mean the checker should be cheap and bounded, not an open-ended critic.

**F-OQ-B16 The published mitigation for relay loss is verbatim artifacts in files or keyed state, under either mechanism.**
> "Communication was handled via files: one agent would write a file, another agent would read it and respond either within that file or with a new file that the previous agent would read in turn." (OQ-17)

> "simply use the output_key to write to the shared session.state so the next agent in the chain knows exactly where to pick up the work." (OQ-43)

> "we find that preserving task-critical information is more important than simply increasing the number of agents, and the benefits of parallelism diminish as coordination failures accumulate." (OQ-41, abstract)

> "If a change can modify the check that judges it, the check is broken." (OQ-19)

Strength: strong as convergent practice. For the skill: the original paste is the check, so the coordinator must hand it to the checker verbatim and the writer must not be the one who relays it. Background OQ-B2 gives Anthropic's original statement of the file pattern.

**F-OQ-B17 The loop needs explicit criteria, a round cap and a fallback; and rounds should build on each other.**
> "A verifier told only to check whether output is good, with no further criteria, will rubber-stamp the generator's output." (OQ-15)

> "A maximum iteration limit with a fallback strategy (escalate to a human, return the best attempt with caveats) prevents this from becoming an infinite loop." (OQ-15)

> "After three rounds, the reviewer asks the author to step back and reconsider the approach." (OQ-20)

> "A reviewer that's asked to find problems will always find *something*." (OQ-06)

> "We point each pass at context from earlier rounds and past failures rather than re-checking everything from scratch. It's cheaper and finds more." (OQ-19)

Strength: strong. The last quote favours continuing the same checker across rounds over spawning a new one each round; a continued checker still has not seen the framer's or writer's reasoning, so its blindness is intact.

**On whether the checker's independence is better preserved by one mechanism:** no source compares the two directly. What the docs establish mechanically (table below): both start without the caller's conversation; a subagent talks only to its caller by default, a teammate can be messaged by any other teammate by design; a checker defined as a subagent can be denied `SendMessage` by its tool list, whereas an in-process teammate always gets it; and the one way a subagent checker loses its blindness is if the coordinator starts it as a fork. This is inference from documented mechanics, not a published measurement.

## Verdict, with confidence and the specific rule the skill should follow (including what the skill should do in a session where the preferred mechanism is unavailable)

**Subagents, not teammates. Confidence: high (about 90%) on that choice.** The product's own criterion sends sequential, dependent work to subagents (F-OQ-B1); a chained, caller-routed pipeline and a skill that spawns subagents are both documented (B2, B3); teams are experimental, off by default, interactive-only and several times the token cost (mechanics table); subagents cannot ask the user while teammates are built to be talked to (B8); and the checker's independence is easier to keep when the only channel is the coordinator and files (mechanics table). The teammates side has one real argument, relay loss through the coordinator (B10), and it is answered by verbatim files and by resuming subagents, not by peer messaging (B16, B9).

**A second, lower-confidence finding (about 60%): the checker is the only expert the evidence says to isolate.** The framer and the requirements writer are consecutive phases of one artifact (F-OQ-B14). The skill can keep them as two subagents if the handoff is verbatim, but the sources would equally support doing the framing in the coordinator, or giving one subagent both steps. This is worth an A/B inside the skill's own tests; it does not change the subagents-over-teammates answer.

The rule:

1. **Mechanism.** Each expert the skill isolates is a non-fork subagent started with the Agent tool and an explicit agent type (`general-purpose`, or a subagent definition shipped with the skill's plugin). Never use a fork for the checker, never `Explore` or `Plan` (one-shot, cannot be resumed), and never ask for teammates.
2. **Verbatim artifacts.** Before anything else the coordinator writes the user's paste, unedited, to a file in its scratch directory. Each stage writes its output to a file. Briefs point at files and do not paraphrase them (F-OQ-B16).
3. **The checker's brief contains three things only:** the path of the original paste, the path of the candidate final prompt, and the pass criteria (every statement in the paste is either carried into the prompt, or listed as an explicit out-of-scope decision; report only omissions and contradictions, each with the quoted line from the paste; do not comment on style). It contains no framing notes, no writer reasoning and no summary by the coordinator (F-OQ-B4, B5, B17). If the skill can ship a subagent definition, give the checker read-only tools and no `SendMessage` so the isolation is enforced, not requested.
4. **Send-back loop.** The coordinator saves the checker's gap list to a file and resumes the writer (SendMessage to its agent ID) with that file path; the writer revises the prompt file; the coordinator resumes the same checker to re-check, so later rounds build on earlier ones (F-OQ-B17). Cap at three rounds; if gaps remain, deliver the prompt with the unresolved gaps listed at the end instead of looping or asking the user.
5. **Turn structure.** In an interactive session subagents run in the background and their results arrive as notifications in a later turn, so the skill's instructions must say "wait for the result before the next stage" at each step and must not assume a blocking call.
6. **When the preferred mechanism is unavailable:**
   - *Agent teams are enabled in the session.* Spawn the experts without a `name` (a named subagent would launch as a teammate, F-OQ-B13) and resume them by the agent ID returned on completion. If one launches as a teammate anyway, keep the same protocol: files only, coordinator routes, the brief tells each expert not to message the others.
   - *The Agent tool is denied, absent, or the skill is itself running inside a subagent at the depth limit.* Do framing and requirements inline in the current context. Run the check as a separate final pass that re-reads the paste file line by line and marks each statement carried / out of scope / missing, quoting the paste, then fix and repeat up to three times. State in the output that the check was not independent. Do not ask the user to open a second session.
   - *Non-interactive (`-p`, Agent SDK).* Subagents work and the caller can wait for them; teams do not form there (OQ-01), so nothing changes.

## What would change the verdict

- Agent teams leaving experimental status with docs that recommend them for sequential pipelines, or that give a way to stop teammates messaging each other.
- A measurement on the skill's own runs showing that requirements are lost in coordinator relay even with file handoffs (then direct writer-checker exchange, still through files, becomes attractive).
- Runs growing from minutes to hours with experts that need accumulated context beyond what a resumed subagent keeps (the case OQ-15 assigns to teams).
- A requirement that the user watch or steer individual experts mid-run (teams are built for that; it conflicts with "never ask the user anything").
- For the secondary finding: an A/B showing that a separate framer subagent yields better final prompts than framing in the coordinator or in the writer, or the reverse.
- For the checker itself: several consecutive evaluated runs in which the blind checker finds nothing the writer missed on the session's model, which is the signal OQ-13 and OQ-17 give for dropping a verifier to an inline pass.
